# Итоговый конспект: Модификаторы доступа в Java (`oop04.modifiers`)

**Пакет проекта:** `second_practice.oop02.modifiers` (практический блок `oop04/modifiers`)

---

## 1. Теоретические основы

В Java модификаторы доступа задают **уровень видимости (инкапсуляции)** для классов, полей, конструкторов и методов. Они позволяют ограничивать доступ к внутренним деталям реализации и предотвращать нерегламентированное изменение данных извне.

### Таблица уровней доступа

| Модификатор | Свой класс | Свой пакет | Классы-наследники (даже в др. пакете) | Весь проект (любой пакет) |
| :--- | :---: | :---: | :---: | :---: |
| **`private`** | ✅ Да | ❌ Нет | ❌ Нет | ❌ Нет |
| **`default` (package-private)** | ✅ Да | ✅ Да | ❌ Нет | ❌ Нет |
| **`protected`** | ✅ Да | ✅ Да | ✅ Да | ❌ Нет |
| **`public`** | ✅ Да | ✅ Да | ✅ Да | ✅ Да |

---

## 2. Подробный разбор модификаторов

### 1. `private` (Максимальное сокрытие)
* **Область видимости:** Только внутри того же класса, где объявлен элемент.
* **Назначение:** Используется для всех приватных полей данных (согласно принципу инкапсуляции).
* **Пример ошибки компиляции:** Попытка обратиться `employee.salary = 1000` из другого класса вызовет ошибку:
  > `'salary' has private access in '...'`

### 2. `default` / `package-private` (Доступ по умолчанию)
* **Область видимости:** Внутри того же пакета (`package`). Специальное ключевое слово не пишется.
* **Назначение:** Ограничение видимости сервисных или внутренних утилитарных методов/классов, которые не должны быть частью публичного API модуля.

### 3. `protected` (Защищенный доступ)
* **Область видимости:** Внутри текущего пакета + в классах-наследниках (`subclasses`), находящихся в других пакетах.
* **Назначение:** Предоставление расширенных прав подклассам для переопределения или использования служебных методов (например, `logTransaction(...)`).

### 4. `public` (Открытый доступ)
* **Область видимости:** Из любого места проекта.
* **Назначение:** Формирование внешнего интерфейса взаимодействия с классом (публичные методы, конструкторы, геттеры и сеттеры).

## 3. Разбор практических решений

### 1. Класс `Person` (`Person.java` и `PersonMain.java`)
* Продемонстрировано распределение 4 полей по всем модификаторам доступа (`publicName`, `protectedAge`, `defaultEmail`, `passportNumber`).
* Прямое обращение к `passportNumber` из `PersonMain` привело к ошибке компиляции, подчёркивая необходимость приватного доступа для персональных данных.

### 2. Класс `Account` (`Account.java` и `BankMain.java`)
* **Приватное поле:** `private double balance` для защиты счета от произвольного изменения.
* **Публичный метод:** `public void deposit(double amount)` — единственная легальная точка пополнения баланса с проверкой условий (`amount > 0`).
* **Защищенный метод:** `protected void logTransaction(...)` — задел для логирования в подклассах.
* **Package-private метод:** `boolean checkBalance(double amount)` — доступен только элементам внутренней системы банковского пакета.

### 3. Класс `Employee` (`Employee.java` и `EmployeeMain.java`)
* Подтверждена невозможность прямого присвоения значения приватной переменной `salary` через точку из другого пакета (`second_practice.oop02.modifiers.practiceMain`).
* Корректная модификация и получение данных реализованы через `setSalary(...)` и `getSalary(...)`.
